# NIDOR — SUPABASE DATABASE & PRODUCT MANAGEMENT

## PROJECT GOAL

Connect the existing NIDOR fragrance website to Supabase and build a functional product management system.

The website already has:

* A cinematic homepage
* Five fragrance experiences
* Existing bottle PNGs and brand assets
* Product descriptions and fragrance notes
* 5 ml and 10 ml decant options
* An existing order interface

Preserve all of these.

**Do not redesign the website or modify its animation system.**

This task is strictly about the database, product data, inventory, and admin product management.

## PHASE 2 — DATABASE SCHEMA

Create a clean, normalized PostgreSQL schema using Supabase.

### Table 1: products

Fields:

* id — UUID primary key
* name — product name
* slug — unique URL-friendly identifier
* brand — fragrance brand
* description — short product description
* fragrance_family — fragrance family
* gender — product audience
* concentration — nullable, only when verified
* top_notes — text array
* heart_notes — text array
* base_notes — text array
* mood — nullable
* occasion — nullable
* season — nullable
* image_url — primary product image
* theme_config — JSONB for existing fragrance-specific visual theme data
* is_active — whether the product is available for sale
* is_featured — whether the product is featured
* display_order — collection ordering
* created_at
* updated_at

### Table 2: product_variants

Each fragrance has separate variants for 5 ml and 10 ml.

Fields:

* id — UUID primary key
* product_id — foreign key referencing products
* size_ml — 5 or 10
* sku — unique stock-keeping identifier
* price_lkr — price in Sri Lankan rupees
* stock_quantity — available units
* is_active — whether this variant is available
* created_at
* updated_at

Constraints:

* A product cannot have duplicate variants for the same size.
* Price must be nonnegative.
* Stock quantity must be nonnegative.
* Only 5 ml and 10 ml sizes are permitted for the initial collection.

Use NUMERIC for monetary values rather than floating-point types.

Do not create separate products for the 5 ml and 10 ml variants.

## PHASE 4 — SUPABASE SECURITY

Configure Row Level Security (RLS) for every table.

Public visitors:

* Can read active products.
* Can read active variants of active products.
* Cannot modify products.
* Cannot modify prices.
* Cannot modify stock.
* Cannot access private admin data.

Administrators:

* Can create products.
* Can edit products.
* Can activate or deactivate products.
* Can update prices.
* Can update inventory.
* Can manage product images.

Use the existing authentication system if one is already present.

If admin authentication does not exist, implement a secure admin role system.

IMPORTANT SECURITY RULES:

* Never expose the Supabase service-role key in frontend code.
* Never use a client-side admin flag as the only authorization mechanism.
* Enforce authorization on the server and through database policies.
* Do not allow users to assign themselves an admin role.
* Do not disable RLS to make the application work.
